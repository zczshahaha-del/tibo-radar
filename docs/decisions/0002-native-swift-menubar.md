# 技术决定：使用 SwiftUI 制作独立菜单栏 App

- 状态：已采用
- 日期：2026-09-10
- 相关 Issue 或 PR：Issue 2

## 当时遇到了什么问题

Python 本地网页已经验证了预测和展示方向，但用户需要的是一个真正的 App：
点击菜单栏图标即可查看，不出现浏览器和终端，也不要求额外安装运行环境。

## 考虑过哪些做法

### 做法一：继续用 Python，加一个菜单栏外壳

- 好处：可以直接复用现有代码，开发较快。
- 问题：仍依赖系统 Python；打包、通知和菜单栏体验不够稳定，交付体积也更大。

### 做法二：用 SwiftUI 重写本机运行层

- 好处：菜单栏、系统通知和 `.app` 打包都是 macOS 原生能力；无需终端和 Python。
- 问题：需要把采集、缓存和核心预测规则移植一份到 Swift，并维护规则一致性。

## 最后选择什么

选择做法二。使用 SwiftUI `MenuBarExtra` 制作菜单栏窗口，用 Swift 并发和
`URLSession` 获取数据，用 `UserNotifications` 发送提醒。Python 原型保留为
预测规则参考和回归对照，不作为原生 App 的运行依赖。

## 为什么这样选择

交付形态是这次需求的核心。原生实现能确保 Finder 双击启动、无 Dock 图标、
无终端窗口，并更容易正确接入 macOS 通知和应用数据目录。

## 这个选择会带来什么影响

- 好的影响：最终产物是独立 `.app`，用户使用路径更短，系统体验更一致。
- 需要承担的问题或成本：修改预测规则时需要同步 Swift 与 Python 两套测试；
  未使用 Developer ID 正式签名的内部构建不能直接公开分发。

## 什么情况下需要重新考虑

如果以后同时支持 Windows/Linux，或者公开数据处理复杂到两套实现难以同步，
再考虑共享本地服务或跨平台运行层。
