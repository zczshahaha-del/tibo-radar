# 技术决定：先做无外部依赖的本地 Python MVP

- 状态：已采用
- 日期：2026-09-10
- 相关 Issue 或 PR：Issue 1

## 当时遇到了什么问题

项目最终适合做成 macOS 菜单栏小工具，但第一步更重要的是验证数据采集、
概率模型和提醒阈值，避免先花大量时间处理签名、打包和菜单栏细节。

## 考虑过哪些做法

### 做法一：直接使用 Swift 制作原生菜单栏应用

- 好处：体验自然，通知和开机启动集成较好。
- 问题：初期迭代概率模型和测试数据成本较高。

### 做法二：Python 标准库、本地网页和系统通知

- 好处：无需第三方依赖，模型容易测试，能快速得到真实使用反馈。
- 问题：第一版没有原生菜单栏图标。

## 最后选择什么

先用 Python 标准库完成可运行 MVP，再根据实际使用效果添加 Swift 菜单栏壳。

## 为什么这样选择

预测质量和少打扰的提醒规则是核心价值。先验证核心，可减少后续原生界面返工。

## 这个选择会带来什么影响

- 好的影响：开发、测试和迁移都简单；不需要安装依赖。
- 需要承担的问题或成本：第一版需要通过浏览器查看完整界面。

## 什么情况下需要重新考虑

当预测和提醒连续使用一周后仍然有价值，就进入原生菜单栏阶段。
